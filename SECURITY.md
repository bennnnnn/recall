# Security Policy

Report vulnerabilities privately. Do not open a public GitHub issue for secrets, auth bugs, or anything that could be exploited.

## Report

Use [GitHub private vulnerability reporting](https://github.com/bennnnnn/recall/security/advisories/new) on this repository.

Include the affected surface (API route, mobile screen, job), how to reproduce, and impact. Do not attach production secrets.

We will acknowledge the report and say whether we are fixing it, need more detail, or do not consider it a vulnerability.

## What this app actually does

- **Backend holds provider keys.** OpenRouter, Google, RevenueCat, R2, Tavily, Mathpix, and similar live only in `apps/api/.env` (Fly secrets in production). The Expo app never embeds those keys.
- **Tokens on device** go in `expo-secure-store`, not AsyncStorage. Access JWTs last 60 minutes; refresh tokens last 30 days in Redis (`jwt_expire_minutes`, `jwt_refresh_expire_days`). Sign out, sign out everywhere, removing one device, refresh-token reuse and account delete all revoke live access tokens too (`core/access_tokens.py`).
- **Sign in with Apple** requires a nonce: the app gives Apple SHA-256 of a random value and sends the raw value; the server accepts the identity token only when they match. Deleting an Apple-linked account on iOS runs Sign in with Apple once more; the server trades that fresh code for the user's Apple token and revokes it (a client-secret JWT signed with `APPLE_PRIVATE_KEY`, `gateways/apple_revoke.py`). Nothing Apple issues is stored. Best effort: Apple being down, or the key unset, never blocks the delete; closing the Apple sheet cancels it.
- **One account per email, joined only by the address's owner.** A Google or Apple sign-in whose id matches no account joins the account holding the same email only when that provider owns the address: Google for Gmail and for a Workspace address whose token's `hd` is its domain, Apple for its relay addresses and iCloud/me.com/mac.com. Otherwise sign-in answers 409 and the app says to sign in the way the account did before (`modules/account/email_authority.py`). A provider's "verified" flag alone is not proof the person controls the address.
- **Per-user data**: every route that takes an id answers another account with 404 (`app/tests/security/`). Account delete removes rows, stored files, the user's Redis keys and the user's entries in the background-jobs stream and its dead-letter queue (their payloads carry chat text); export covers everything stored about the user. A registered push token moves to another account only from the same app install (its device id); a token row saved before device ids existed stays with its owner (`repositories/push_tokens.py`).
- **Limits survive deleting the account.** So that deleting an account and signing in again cannot reset today's limits, account delete keeps the same counts under one Redis key per sign-in, `quota_carry:<HMAC-SHA256 of "quota-carry:google:<sub>" or "quota-carry:apple:<sub>", keyed with the server's JWT secret>`, and, when the address is one a provider owns by its domain, one for the account's email address, `quota_carry:<HMAC-SHA256 of "quota-carry-email:<address>", same key>`, the address trimmed and lower-cased first (nothing else: no provider's own rules such as Gmail's dots). The owner is decided by the rules that let a new sign-in join an account by email (`modules/account/email_authority.py`), read from the account's stored address: Google for `@gmail.com` and `@googlemail.com`, Apple for `@icloud.com`, `@me.com`, `@mac.com` and its private relay. Those addresses are never given to someone else, so the key is kept whichever provider the account signed in with (an Apple ID on a Gmail address is common). A provider that only verified any other address does not show the person still holds it (a stale work address, a lapsed domain), and an email key would hand that account's used-up day and live talk month to whoever signs up on the address next. So an account keeps only its sign-in keys when it has no email, when no provider owns its address, or when its address is a Google Workspace one: Google owns that only through the sign-in token's `hd` claim, which the account does not keep, so a delete cannot tell. Each key holds only counts: today's tokens, uploads, voice, web searches, image generations and photo lookups, and this month's live talk seconds. None holds the raw Google/Apple id, the email address, the user id or any content. When that sign-in, or any sign-in on an address that has a key (Google after a deleted Apple account on an iCloud or Gmail address, Apple after a deleted Google account on either), creates a new account or joins the existing account that holds its email, that account's counters are raised to those counts (each to the larger value, never lowered and never added together) and every key used is deleted. A key left unused expires when the UTC month ends, after at most 35 days (`modules/account/quota_carryover.py`). The keys are stored first: when Redis cannot store them, the delete is refused with 503 `unavailable` before anything is deleted or signed out, and the app asks to try again. Likewise, when Redis cannot restore the counts to that account, sign-in is refused with 503 `sign_in_unavailable` and no account is made or joined; the keys stay for the retry.
- **No user can spend for everyone.** `DAILY_GLOBAL_SPEND_USD` stops new chat turns, images, voice, live talk, scans and background model jobs for the rest of the UTC day, so nothing a client sends may add to it without bound: a chat turn reserves its own daily tokens before it runs, live talk is charged by the minutes its session reserved (not per turn the phone posts, and a session's saved turns are capped), and a scanned PDF takes an image-upload slot before it is OCR'd (`services/quota/`, `gateways/llm_spend.py`). Text with a NUL character is refused at the request (422, or an error frame on the chat WebSocket) instead of failing its save after the reply was already paid for, and a PDF's extracted text drops NUL before it is saved (`models/schemas/text.py`).
- **Error reports and logs carry no user text.** Sentry events carry no request bodies and no stack-frame variables; a logged line reaches Sentry as its template, without its arguments, and error text is cut at 300 characters (`core/sentry.py`). Log lines at INFO and above give ids, kinds and lengths, never a reminder's title, an email's subject or a message (`tests/architecture/test_log_privacy.py`), failed SQL hides its parameters, and the access line logs the route template, not the path.
- **Production boot** refuses `DEV_AUTH_ENABLED` and `MOCK_LLM_ENABLED`. CORS must be an explicit origin list, not `*`.
- **LLM structured output** is validated with Pydantic before it is written. Untrusted attachment and OCR text is wrapped before it reaches the model. The model's `generate_image` tool is offered only when the user's own message asks for a picture, and a tool the turn was not offered never runs, so text in a web result or a file cannot spend the user's image allowance (`modules/chat/tool_loop/`).
- **Nothing the model writes loads a URL by itself.** Injected text can tell the model to put the user's memory or schedule into a URL, so the app treats every model-written URL as a possible leak, not just an IP/UA exposure:
  - *Images.* The phone auto-loads only images from the Recall API's own origin (every picture the server adds is an attachment there: photo lookups, answer photos, generated images, uploads) and inline raster `data:`/`blob:` images. Any other `https:` image is a placeholder naming its host that loads on tap; `http:` and every other scheme never load (`apps/mobile/lib/images/imageUriPolicy.ts`). An `[Image: …]` marker naming another host is never drawn as a photo (`lib/messageAttachments.ts`).
  - *Link previews* (fetched by the server, `GET /link-preview`) are asked for only for a link the user wrote or one of the reply's search sources; any other link is a plain card that fetches nothing (`lib/linkPreviewTrust.ts`). Each preview fetch has an 8s overall deadline and a user has at most three open at once.
  - *Saved replies.* Before a reply is saved, a finalize pass drops `[Image: …]` lines that are not Recall attachment markers, turns markdown images and `<img>` tags that could reach a host into links, and drops a `sources` fence on a turn the server did not search; fenced and inline code are left as written (`modules/chat/untrusted_media.py`). History therefore auto-loads nothing for the web client either. While a reply streams, the web client (slice 1) and app builds older than this policy still load a markdown image; the web renderer needs the phone's image policy before it ships widely.
- **No arbitrary code execution.** Chat code is rendered only. HTML/CSS/JS may run inside the sandboxed preview WebView (dev/production build, not Expo Go). Python and shell are never executed. The preview holds no app token, and page script cannot navigate it away or open other URLs and apps (`allowHtmlRunNavigation` in `apps/mobile/lib/webView.ts`).
- **Rich previews** (Mermaid diagrams, charts, SMILES drawings) load a page the app writes to its cache directory from vendored libraries (`apps/mobile/lib/previewPageFile.ts`). A diagram's source, a chart's spec or a SMILES reaches the page as JSON data, never as page markup, and never touches disk; each page's CSP allows no network. Android needs `allowFileAccess` to open a `file://` page. A diagram, chart or SMILES page may load only its own file (`allowPreviewPageNavigation` in `apps/mobile/lib/webView.ts`; iOS grants read access to that file alone, and neither platform lets it read other files). Links never navigate a page: one the user taps opens only if it would open from a chat message (`apps/mobile/lib/linkSchemePolicy.ts`). A PDF is untrusted content, so its preview is no file at all: the WebView gets one HTML string holding pdf.js and the PDF as inert base64 text (`apps/mobile/lib/pdfPreviewHtml.ts`, `usePdfPreview` in `apps/mobile/features/attachments/hooks/`), with no file access on either platform (no `allowFileAccess` or `allowFileAccessFromFileURLs`, no iOS read access), and its CSP lets it fetch nothing: no network, no `file:`, images and fonts only from `data:` and `blob:` (`PDF_PREVIEW_CSP`). pdf.js runs with `isEvalSupported` off, and a file over the upload cap is not previewed.
- **Symbolic math** is server-side SymPy in isolated workers. The phone only renders.

## Out of scope for this file

App Store / Play Store signing, RevenueCat dashboard access, and Fly/Neon/Upstash IAM are operator secrets. Rotate them in those consoles; do not commit them.
