## Findings

### REL-01 — One chat message can stall a machine's event loop for minutes to forever (super-linear CPU in the on-loop readers)
- Severity: Critical (one authenticated free user takes an `app` machine offline; repeatable per machine)
- Confidence: Medium (each mechanism measured or read directly; the full chat-path chain was traced by reading, not executed end to end)
- Locations:
  - Physics ReDoS: `apps/api/app/modules/physics/extractors/common.py:123-126` (`_LABEL_GAP`), `:152` (`_LABEL_GAP.fullmatch(text[end:candidate.start()])`), reached from `:221` in `_find_value_with_specific_unit` whenever a keyword tuple is passed (that helper is called from 30 physics extractor files, e.g. `apps/api/app/modules/physics/extractors/forces.py:86-90` with `("mass","object","body")`, `apps/api/app/modules/physics/extractors/energy.py:202-204`).
  - SymPy on the loop (maths readers): `apps/api/app/modules/math/tools/extractors/graph.py:194-195` (`_parse_expression`, evaluate=True) and `:202` (`solve(Eq(lhs, rhs), y)`), called from `:342`; `:242-243`; `apps/api/app/modules/math/tools/graph_followup.py:97-104`; `apps/api/app/modules/math/tools/extractors/calculus_applications.py:130-131`.
  - The on-loop entry points (sync calls inside `async def`, no `run_sympy`, no timeout): `apps/api/app/modules/math/tools/prompt.py:238/265/294` (`build_math_augmentation` → `resolve_graph_followup`, `extract_math_intent`), `apps/api/app/modules/chat/tool_loop/selection.py:154`, `apps/api/app/modules/math/tool.py:616` (sympy tool `invoke`), `apps/api/app/modules/physics/prompt.py:62/76/102` (`needs_physics`, `extract_physics_intent`), `apps/api/app/services/routing.py:401/405/436` (`_physics_solves` runs `solve_physics` in-process).
  - Guard that does not bound the cost: `apps/api/app/modules/math/solve/parse.py:123-125, 152-161` (blocks `__`, `[`, long `e` exponents; not power towers), `:169/179-184` (`parse_expr(..., evaluate=True)`).
  - Physics solvers on the loop too: `apps/api/app/modules/physics/solvers/drag.py:4` ("Chat already runs physics in the SymPy worker" — false for routing/follow-ups) and `:26-52` (`_drag_identities_hold`: 11 `simplify` + 6 `limit` calls, first drag question per process); `apps/api/app/modules/physics/followup.py:128-134`.
- Evidence:
  - `_LABEL_GAP = re.compile(r"(?:[\s,:=.]+|(?:of|is|are|...|to)\b)*", re.I)` is `(a+)*` under `fullmatch`. Local timing of that exact pattern on `","*n + "x"`: n=18 0.03 s, n=20 0.11 s, n=22 0.46 s (doubles per character; n=30 ≈ 2 min, n=40 ≈ days). Commas survive the physics normalizers (`services/symbolic_text.py:114-124` collapses only whitespace; `modules/physics/numbers.py:128-135` only ungroups digit commas). A message like `What is the net force on a body of mass,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,x 5 kg accelerating at 2 m/s^2?` reaches it: "force of"/"net force" is a force cue (`forces.py:19-27`), the gap between the keyword `mass` and `5 kg` holds no other match, so `fullmatch` runs.
  - `extractors/graph.py:342`: any "graph … = …" containing `y` goes to `_solve_for_y_as_function_of_x`, which parses both sides with SymPy (`evaluate=True`) and calls `solve`. Installed SymPy 1.14: `parse_expr("9**9**7 + x")` took 1.7 s, `parse_expr("9**9**8 + x")` took 56.4 s (scratch `sympy_pow_probe.py`); `9**9**9` is ~40x that and `9**9**9**9` never returns. The 256-char limit (`core/settings/stem.py:9`) does not help.
  - `core/sympy_executor.py:1-12` states the rule this breaks: "a hung SymPy call starves unrelated async work".
- Impact: one uvicorn event loop serves every socket and request on the machine (SCALING.md "CPU"). While it spins: every WebSocket and SSE stream on the machine freezes, `/health` and `/health/ready` time out (Fly stops routing but does not restart the Machine, PRODUCTION.md §4), the 10 s `chatprep` refresh stops so other machines can start a second turn on the same chats, and the turns on the machine are lost when someone restarts it. The same user repeats it on every machine. It can also happen by accident with large pasted text (physics readers scan up to 4 000 chars, `services/symbolic_text.py:8-11`).
- Fix: class fix at the reader seam: run the maths/physics/chemistry readers (`extract_math_intent`, `extract_physics_intent`, `needs_physics`, `resolve_graph_followup`, `solve_physics` in routing/follow-ups) inside the bounded, killable pool (`core/sympy_executor.run_sympy`, or a second "reader" pool behind the same `BoundedSympyExecutor` seam, SCALING.md item 9) with a short timeout and "no verified answer" on timeout. Instance fixes: make `_LABEL_GAP` linear (`(?:[\s,:=.]|(?:of|is|…)\b)*` — one char per iteration — or an atomic group `(?>[\s,:=.]+)`); in `_parse_expression` reject `**`/`^` chains whose evaluated exponent can exceed a bound (or parse with `evaluate=False` and check `Pow` sizes) on every path, not only inside the worker; precompute `_drag_identities_hold` at import/boot or move it to a test.
- Effort: M (move readers behind the pool; regex and power-tower guards are S)
- Verify: unit tests that `_find_value_with_specific_unit("A body of mass" + ","*40 + "x 5 kg", "kg", ("mass",))` returns in < 50 ms and that `extract_math_intent("graph y = 9^9^9 + x")` returns within the reader timeout; a property test (hypothesis) feeding long punctuation runs to every compiled reader regex; a loop-lag metric (e.g. a 100 ms heartbeat task logging lag > 250 ms) on the API with an alert.

### REL-02 — A request's DB session stays checked out (idle in transaction) for the whole response, including SSE streams and slow provider calls
- Severity: High
- Confidence: High for the mechanism (library code read); Medium for how often it bites (depends on user-cache misses and SSE share)
- Locations:
  - The source: `apps/api/app/core/deps.py:37-62` — `get_current_user` depends on `get_db` (`apps/api/app/core/db.py:46-48`); on a user-cache miss it runs `users_repo.get_by_id(session, …)` (`deps.py:58`, `repositories/users.py:22-23`, a `session.get`) which autobegins a transaction and checks a pooled connection out. Nothing commits or closes it before the response ends: FastAPI 0.142.2 gives a `yield` dependency without `scope` the "request" scope (`.venv/.../fastapi/dependencies/models.py:229-234`) and closes that stack only after `await response(scope, receive, send)` (`.venv/.../fastapi/routing.py:146-152`).
  - SSE chat: `apps/api/app/modules/chat/stream_api.py:262-326` (both routes take `Depends(get_current_user)`; the StreamingResponse lasts the whole turn, up to `chat_stream_max_seconds` 600 s, `core/settings/llm.py:50`, plus tool loop and finalize). `apps/web` slice 1 uses SSE for every turn, and phones fall back to SSE past the socket cap.
  - Export: `apps/api/app/modules/account/api.py:438-445` — the generator deliberately opens a session per page "so a slow client download cannot pin a Neon connection for the stream lifetime" (`apps/api/app/modules/account/export.py:258-259`), but `get_current_user`'s own session pins one anyway on a cache miss.
  - Slow non-streaming routes: `/images/generate` (`modules/images/api.py:22-26`; provider read timeout 120 s, `gateways/image_gateway.py:18`), `/{math,physics,chemistry}/scan/read` via `get_consented_user` (`modules/account/consent.py:39-50`, which also `refresh`es on the same session; 20 s deadline, `core/settings/stem.py:54`), `/memories/instruct` (LLM), `/speech/*`, `/auth/me/sync-subscription` (RevenueCat), `/link-preview` (8 s fetch).
  - Same class inside services: `apps/api/app/modules/chat/service.py:216-219` — `GET /chats/{id}/messages` reads the chat (opens the transaction) and then waits `wait_for_inflight_stream` (≤10 s) and `wait_for_pending_finalize` (≤10 s Redis poll) on it (`modules/chat/finalize_registry.py:40, 65-67, 140-180`); `apps/api/app/modules/attachments/reuse.py:30-54` — up to 10 sequential R2 `copy_object` calls (each up to 3 × (5 s + 20 s), `gateways/storage_gateway.py:169-187`) inside the chat turn's open transaction (`modules/chat/turn_prep/attachments.py:175-198`); `apps/api/app/modules/chat/compaction.py:37-89` — the `compress` job holds its transaction across the summarization LLM call (≤60 s, `core/settings/llm.py:61`).
- Evidence: `core/deps.py:51-58`:
  `cached = user_cache.cached_user(user_id)` … `user = await users_repo.get_by_id(session, user_id)`; CLAUDE.md "Transaction ownership": "Slow provider calls should run outside an open DB transaction".
- Impact: each machine has 30 connections (`core/settings/infrastructure.py:17-19`, pool timeout 5 s). Thirty concurrent SSE turns or image generations that started on a cache miss (the user cache is per machine, 60 s TTL, not refreshed on hit — `core/ttl_cache.py:27-35`) exhaust it; every other request on the machine, including turn finalize writes (`turn_settle.py:294-301`) and `/health/ready` (`routers/health.py:33-35`, same pool), waits 5 s and fails with 503, so replies are lost and the machine is marked unready. Through Neon's transaction-mode pooler each idle-in-transaction connection also holds a server connection, so (N app machines × long streams) can starve the database for the whole fleet (SCALING.md "Postgres connections").
- Fix: make `get_current_user` load the user in its own short session and return a detached row (or commit/close after the read), and give `get_db` `Depends(get_db, scope="function")` for routes that stream; in `list_messages_page` release the session before the waits; move `copy_object` out of the transaction in `ensure_unlinked_copies` (copy first, then one short insert transaction); in `compress_chat_history` read, close, summarize, then write in a second short session. Seam: `core/deps.py`, `core/db.py`.
- Effort: S–M
- Verify: a test that a streaming route with a cold user cache shows `engine.pool.checkedout() == 0` while the body is still streaming; production metric: pool `checkedout()` gauge and Postgres `idle in transaction` count (alert > N).

### REL-03 — Every blocking call shares one 5-thread default executor whose timeouts do not free threads; one or two users' turns starve sign-in, R2 and file reading for the whole machine
- Severity: High
- Confidence: High (code and library read; 5 threads is the project's own figure for one vCPU)
- Locations (all `asyncio.to_thread` → the loop's default `ThreadPoolExecutor`, `min(32, cpu+4)` = 5 on Fly's shared-cpu-1x, as `core/settings/attachments.py:80-82` and PRODUCTION.md's R2 row state; uvloop keeps DNS off it, nothing else):
  - DuckDuckGo search: `apps/api/app/gateways/web_search_gateway.py:137-141` (`asyncio.wait_for(asyncio.to_thread(_search_duckduckgo_sync…), 8s)`), `:115-128` (up to three `DDGS` calls per query). ddgs 9.16 walks its engines in batches of two, `wait(timeout=8)` per batch, and its `with ThreadPoolExecutor` waits for stragglers on exit (`.venv/.../ddgs/ddgs.py:182-198`), so the executor thread stays busy tens of seconds after `wait_for` gave up. A turn fans out 3–4 queries at once (`modules/web_search/search_cache.py:139`), and once a user's daily Tavily allowance is used (20 search turns a day on Free, `core/settings/plans.py:21`), every search goes to DuckDuckGo "uncapped (latency only)" (`search_cache.py:67-100`), so this is a routine path, not only an outage path.
  - Document parsing on the chat path: `apps/api/app/modules/attachments/content.py:207-215` (5 s `asyncio.timeout` around `to_thread(extract_text_details…)`; on timeout the pypdf/python-docx parse keeps running), up to 10 files gathered at once (`modules/chat/turn_prep/attachments.py:222, 270`; `models/schemas/chats.py:124`).
  - R2 (boto3): `apps/api/app/gateways/storage_gateway.py:255-268` (three executor hops per read: `get_object`, `body.read`, `body.close`), `:189-282, 301-316`; each call may retry 3 × (5 s connect + 20 s read) (`:169-187`). Used by turn attachments, thumbnails (`modules/attachments/thumbnails.py:103-119`), vision (`modules/attachments/vision_input.py:95-105`), uploads, deletes.
  - Google sign-in: `apps/api/app/gateways/google_auth.py:102-112` (cert fetch + verify in a thread, 12 s budget → 503).
  - Pillow: `modules/attachments/vision_input.py:100`, `modules/attachments/thumbnails.py:114`; OCR rendering `modules/attachments/ocr.py:200`.
- Evidence: `web_search_gateway.py:24-25` says the bound exists — "a stalled DDG socket must not hang TTFT or pin a shared thread-pool worker indefinitely" — but `wait_for` only stops the await; `core/sympy_executor.py:9-12` already documents that "cancelling the await leaves the underlying thread running". `core/settings/attachments.py:8-11` claims the parse is "bounded by this timeout so a large or adversarially crafted file can't block the event loop": the await is bounded, the thread and its CPU/GIL share are not, and the 5 s budget includes time queued behind other jobs.
- Impact: the executor queue is unbounded and FIFO. Two news questions from users past their Tavily cap (3–4 DuckDuckGo threads each, held ~10–60 s) or one 10-PDF turn fill all five threads; then on that machine every Google sign-in waits past its 12 s budget and answers 503, every attachment read and thumbnail queues, and every chat-path parse times out. A parse that timed out is reported to the model as unreadable: for a PDF the prompt says "No extractable text layer — this is likely a scanned or image-only PDF" (`content.py:219-220` → `:390-395`), so the user is told their text PDF is a scan. On one vCPU the CPU-bound parse threads also take CPU from the event loop.
- Fix: give each class of blocking work its own bounded executor with a bounded queue and fail-fast admission (e.g. `core/` helper `run_blocking(pool, fn, timeout)` raising "busy"): one small pool for R2/boto3 (or move R2 to an async S3 client), one for document/image CPU work (or the SymPy-style killable process pool for parsing), and a dedicated one for sign-in; cap DuckDuckGo with a per-machine semaphore and per-user rate (or drop the DDG fallback for capped users); distinguish "parse timed out" from "no text layer" in `format_attachment_lines`. Seams: `gateways/storage_gateway.py`, `gateways/web_search_gateway.py`, `modules/attachments/content.py`, `gateways/google_auth.py`.
- Effort: M
- Verify: a test that a saturated document pool does not delay `verify_google_id_token`; a metric for executor queue depth and wait time per pool; a test that a parse timeout produces a "could not read in time" note, not the scanned-PDF note.

### REL-04 — Model health (the chat circuit breaker) records the wrong alias, counts mid-stream failures as successes, measures reply length as latency, and never half-opens
- Severity: High
- Confidence: High (logic read end to end); Medium on how often the latency rule trips in production
- Locations: `apps/api/app/modules/chat/stream_paths.py:239, 269, 289, 308-317`; `apps/api/app/gateways/litellm_gateway.py:241-245, 254-271`; `apps/api/app/services/model_health.py:17-18, 50-86, 99-109`; consumers `apps/api/app/services/routing.py:505-512`, `apps/api/app/modules/billing/plan.py:255-272`, `apps/api/app/modules/chat/turn_load.py:238-287`, `apps/api/app/modules/chat/turn_prep/context.py:259-277`.
- Evidence:
  - One sample per turn, for `stream_meta.get("model_alias") or requested_model` (`stream_paths.py:313`). `stream_chat_completion` sets `stream_meta["model_alias"]` only to the alias that produced content (`litellm_gateway.py:244`) or, when every alias failed, to the last one (`:268-270`). A primary that fails before its first token while a fallback answers is never recorded as failing; a total failure is charged to the last fallback, not the primary.
  - `stream_ok = True` at the first token (`stream_paths.py:269`); a provider failure after that raises out of the loop before `:289`, so the turn is recorded as `success=True` — for `requested_model` (the primary) even when the fallback was the one that broke.
  - `latency_ms=(time.perf_counter() - started) * 1000` (`:314`) is the whole reply including thinking, but `get_health` marks an alias unhealthy when that p50 reaches 30 s (`model_health.py:80`): a model whose answers are long (lessons, code, a reasoning model) reads as "slow provider".
  - No time window: `get_health` reads all 40 members of the zset (`:53`) whatever their age; the key's TTL is 24 h (`:18`) and is refreshed on each sample.
  - No half-open: unhealthy aliases are dropped from Auto (`routing.py:512`) and from fallbacks (`plan.py:271`), so they get no new samples except from users who pick them explicitly; an alias marked unhealthy during a 10-minute incident stays out of Auto until its key expires 24 h after its last sample.
- Impact: during a primary-model outage every turn first waits for that model to fail (5 s connect, 30 s idle per chunk in production per `fly.toml` `[env]`, 8 s first-content for reasoning aliases, `core/settings/llm.py:47-56`) and the breaker never opens, so time-to-first-token rises for every user of that model for the whole incident and the provider keeps receiving doomed requests. Conversely a healthy but slow-writing model can be removed from Auto for a day, shifting traffic and cost to other models with no alert. At 100k DAU both are fleet-wide because the samples are shared in Redis.
- Fix (seam `services/model_health.py` + `gateways/litellm_gateway.py`): record one sample per attempted alias inside `stream_chat_completion` (failure for each alias that failed before content, success/failure for the one that streamed, failure on a mid-stream break); measure time-to-first-content, not reply duration; weight or window samples by time (e.g. only the last N minutes); add a half-open probe (let one turn per interval through to an unhealthy alias, or decay unhealthy after T minutes).
- Effort: S–M
- Verify: unit tests on `stream_chat_completion` with a failing primary and a working fallback asserting a failure sample for the primary; a test that a 60 s healthy stream stays healthy; a test that an alias with only old failures becomes routable after the window; dashboard of per-alias error rate and TTFT.

### REL-05 — A chat turn reads every attached document whole and at once: no per-turn byte budget, no daily cap on document uploads
- Severity: High (a single user can push an `app` machine into the OOM killer; the documented consequence is losing every unsaved reply on it)
- Confidence: Medium (bounds read from code; peak RSS not measured)
- Locations: `apps/api/app/models/schemas/chats.py:124` (10 attachments per message), `apps/api/app/core/attachment_limits.py:3` (10 MiB each), `apps/api/app/modules/chat/turn_prep/attachments.py:222-253` (all unverified uploads read concurrently and kept in `bytes_by_key`), `:270-288` (`asyncio.gather` of `format_attachment_lines` for every row), `apps/api/app/modules/attachments/content.py:373-377` (whole object read, then parsed), `apps/api/app/gateways/storage_gateway.py:261-266` (`body.read()` of the whole object), `apps/api/app/modules/attachments/upload.py:72-78` (only images take a daily slot; PDFs, DOCX, XLSX, PPTX and text do not), `apps/api/app/modules/attachments/reuse.py:14-54` (a Library file can be re-attached to every message).
- Evidence: the image path was already fixed for exactly this (`modules/attachments/vision_input.py:8-15`: "A phone photo can be 10 MB and a send can carry ten … held about 370 MB on a 1 GB machine" → one photo at a time, `attachment_vision_max_turn_bytes` 20 MB, `core/settings/attachments.py:39-40`). Documents have neither: a turn with ten 10 MiB PDFs holds ≥100 MiB of raw bytes at once plus up to five concurrent pypdf/python-docx object trees (5 executor threads). PRODUCTION.md "Load and abuse limits" puts the machine at 550–850 MB before any request.
- Impact: one turn of ten large documents approaches the headroom; a user with several chats open (5 sockets per machine, SSE uncapped) or a few users attaching large files at the same moment exceed it. The kernel kills the API process (or a SymPy worker): every in-flight turn on the machine is lost and its `chatprep` locks block those chats for 30 s (SCALING.md "Per machine on purpose"). Nothing limits how often a user can do it beyond 30 messages a minute.
- Fix: in `turn_prep/attachments.py`, process document attachments sequentially (or with a semaphore of 1–2) and enforce a per-turn byte budget like the vision one (a setting next to `attachment_vision_max_turn_bytes`); drop each file's bytes as soon as its excerpt is taken; for the chat excerpt read only what `PDF_EXTRACT_MAX_PAGES`/`MAX_EXTRACT_CHARS` need (ranged GET or size check before download); add a daily document-upload allowance (`services/quota/counters.COUNTERS`). Seam: `modules/chat/turn_prep/attachments.py`, `core/settings/attachments.py`.
- Effort: S–M
- Verify: a test that ten 10 MiB fake documents never hold more than the budget at once (count live buffers through a fake gateway); a load test measuring RSS for a 10×10 MiB PDF turn.

### REL-06 — Tool calls and searches on the time-to-first-token path have no overall deadline; the 20 s "invoke timeout" only stops new calls from starting
- Severity: Medium
- Confidence: High
- Locations: `apps/api/app/modules/chat/tool_loop/calls.py:125-146` (`invoke_deadline` checked in `_refusal`, `:166`, before each call), `:180-185` (`await mcp_registry.invoke_validated(...)` with no timeout), `apps/api/app/gateways/mcp/registry.py:59-90` (no timeout), `apps/api/app/core/settings/llm.py:14-19`; adapters `apps/api/app/modules/web_search/tool.py:87-113`, `apps/api/app/modules/images/gen_tool.py:51`, `apps/api/app/modules/images/search_tool.py:55`; heuristic search before the loop `apps/api/app/modules/chat/prompt_builder.py:130`, forced search `apps/api/app/modules/chat/tool_loop/rounds.py:117, 140`.
- Evidence: the only bounds are per-phase httpx timeouts — Tavily 12 s each for connect, write, pool and every read (`gateways/web_search_gateway.py:23, 163-164`), then DuckDuckGo 8 s (`:137-141`); image generation 120 s per read (`gateways/image_gateway.py:18, 50`); photo lookup tries candidates one after another with 8 s each (`modules/images/search.py:119-127`). Up to 2 rounds × 4 sequential calls (`core/settings/llm.py:14, 18`) plus the forced search.
- Impact: in a Tavily or OpenRouter-images brownout a turn can sit in "Searching…" for 30–90 s before any token; the phone only says "still working". The prepare lock, the quota reservation and the socket are held for that time, and a slow dependency turns directly into user-visible latency on every search turn rather than a fast "search unavailable".
- Fix: wrap each `invoke_validated` in `asyncio.timeout(remaining)` where `remaining` is the round's deadline, and give the whole pre-stream phase (heuristic search + tool rounds + forced search) one budget (`ChatTurnDeps`/`stream_paths.run_tool_loop_path`); give Tavily an overall `asyncio.timeout` in the gateway. Seam: `modules/chat/tool_loop/calls.py`, `gateways/web_search_gateway.py`.
- Effort: S
- Verify: a test with a fake search adapter that sleeps 60 s asserting the round returns its refusal message within the deadline; TTFT p99 broken down by "tool_loop_done" phase (`turn_timing`).

### REL-07 — The per-machine SymPy pool has no per-user share; one user can keep it busy or cold for everyone else on the machine
- Severity: Medium
- Confidence: Medium
- Locations: `apps/api/app/core/sympy_executor.py:269-343` (`run`: 2 s wait for a slot, then the solve; any exception or cancel kills the slot at `:333-340`), `:212-226` (`_warm_slot`: the next caller on a killed slot waits up to 20 s for a new worker's ~4 s SymPy import), `:228-262` (`_kill_slot` runs `proc.join` and `pool.shutdown(wait=True)` synchronously on the event loop), `apps/api/app/core/settings/stem.py:19-24` (3 workers, 5 s solve, 2 s wait); callers with no user key: `modules/math/tools/prompt.py:425`, `modules/math/tool.py:100`, `modules/chat/tool_loop/calls.py:99`, `modules/chat/finalize_subjects.py:140, 217`, `modules/physics/prompt.py:40, 92`, `modules/chemistry/context.py:310`.
- Evidence: a turn can call `run_sympy` several times (pre-solve, the tool-call match check, finalize checks). - Fix: a per-user concurrency cap on `run_sympy` (pass the user id; at most one slot per user per machine, others queue or decline for that user only), and do not kill the worker on a plain caller cancel when the job is about to finish (let it complete, discard the result) — kill only on timeout. Move `_kill_slot`'s joins to `asyncio.to_thread`. Seam: `core/sympy_executor.py` (`BoundedSympyExecutor.run`).
- Effort: S
- Verify: a test with a fake executor that two users with saturating jobs leave a slot for a third; metric `sympy queued` (already logged at `:327-331`) per user.

### REL-08 — Withdrawing AI-data consent (or turning memory or web search off) is not honoured for up to 60 s on other machines' SSE, voice and scan paths
- Severity: Low (privacy commitment, short window, subset of paths)
- Confidence: High
- Locations: `apps/api/app/modules/chat/stream_api.py:267, 289` (SSE passes the cached `user` into the turn), `apps/api/app/modules/chat/turn_load.py:79-84` (`if user is not None and consent.has_ai_data_consent(user): return user` — only a refusal re-reads the row), `apps/api/app/modules/account/consent.py:39-50` (`get_consented_user` for `/speech/*` and `/{subject}/scan/read`: re-reads only when the cached row has no consent), `apps/api/app/core/deps.py:51-56`, `apps/api/app/core/user_cache.py:24` (60 s), `apps/api/app/modules/account/profile.py:54-62, 66-77` (web-search switch and consent fields come from the same row).
- Evidence: `consent.py:3-11` promises refusal "until the account agrees, and again after it withdraws"; SCALING.md's user-row line says "Consent is re-read from the row before a turn is refused" — true for an agreement made elsewhere, but a withdrawal is never re-read while the cached row still says yes. The WebSocket path is not affected: it passes `user=None` and `_load_user` reads the row every turn.
- Impact: after a user withdraws consent (or turns memory or web search off) through one machine, another machine's cached row keeps sending their messages, voice and photos to OpenRouter/OpenAI, injecting memory and searching the web for up to a minute. Small window, but it contradicts the stated guarantee; with more machines the share of requests on a stale row grows.
- Fix: treat "consent revoked / memory off / search off" as a write that must be seen everywhere: bump a per-user Redis generation key on `PATCH /auth/me` and check it in `user_cache.cached_user` (SCALING.md change 4, already designed), or re-read these three columns on the SSE/voice/scan entry points as the WS path does. Seam: `core/user_cache.py`.
- Effort: S
- Verify: a two-process test (two caches) where withdrawal on one makes the next SSE turn on the other answer `consent_required`.

### REL-09 — No saturation signals: event-loop lag, DB pool, thread pools, Redis pool and per-machine sockets are not measured
- Severity: Medium
- Confidence: High
- Locations: no metrics exporter or gauges in `apps/api/app` (no Prometheus/StatsD/OpenTelemetry; no `engine.pool.checkedout()`, executor queue, or loop-lag sampling — repository-wide search); the only saturation log is `core/sympy_executor.py:327-331`. Per-turn phase timing exists (`modules/chat/turn_timing.py:34-60`) but logs only completed turns.
- Evidence: SCALING.md "CPU": "Measure before moving any of it", and its changes 2–5 and 9 are all gated on measurements; PRODUCTION.md §4 asks the owner to "watch Fly's proxy concurrency metrics". Nothing in the API emits the numbers those decisions need, and REL-01/02/03/05 each fail silently until requests time out.
- Impact: at 100k DAU the first signal of loop stalls, pool exhaustion or executor starvation is user-visible 503s and timeouts, with logs that show symptoms ("Dependency unavailable", "timed out") rather than the saturated resource; capacity planning for N machines is guesswork.
- Fix: add one `core/metrics.py` (or Sentry custom metrics) with: a loop-lag heartbeat task (sleep 0.1 s, record overshoot), DB pool `checkedout()/overflow()` gauges, default-executor `_work_queue.qsize()`, SymPy free slots, open sockets per machine, Redis pool `_in_use_connections`; sample every 10 s from the lifespan; alert on loop lag > 250 ms and pool checkout waits.
- Effort: S
- Verify: the gauges appear in the dashboard; a synthetic blocking call in staging raises the loop-lag alert.

### REL-10 — The data export has no per-user rate or concurrency limit beyond the global 240 requests/minute
- Severity: Medium
- Confidence: High (absence of a limit); Medium (cost per export not measured)
- Locations: `apps/api/app/modules/account/api.py:438-445` (route: only `Depends(get_current_user)`), `apps/api/app/modules/account/export.py:46-57` (up to 500 chats × 2,000 messages, 5,000 memories, 2,000 todos, 2,000 attachments, 2,000 events per export), `:252-305` (page-by-page queries and one `json.dumps` per row on the event loop), `:227-229` (one `presign_download` → default-executor hop per attachment), `apps/api/app/core/settings/edge.py:15` (`rest_rate_limit_per_minute = 240`, the only bound).
- Evidence: every other expensive route has its own limiter (sign-in `account/api.py:53-76`, chat `core/chat_rate_limit.py`, voice `modules/speech/gates.py:46-58`, scan reads `services/scan_read.py:96`, link preview `modules/link_preview/api.py:31`, memory instruct `modules/memory/api.py:116`); the export has none.
- Impact: one account can start dozens of exports at once (each a long StreamingResponse, each up to ~1M rows read in 200-row pages and serialized on the shared event loop, plus up to 2,000 executor hops). That is CPU on the loop for every user of the machine (REL-01's failure mode, at a slower rate), sustained DB load, and default-executor pressure (REL-03). With REL-02 each one can also pin a DB connection for its whole length.
- Fix: one export at a time per user (a Redis `SET NX` lock with TTL, like the link-preview concurrency set) and a daily or hourly export cap; consider producing the export in a worker job to a presigned R2 object instead of streaming from the API. Seam: `modules/account/api.py`, `core/rate_limit.allow_request_fail_closed`.
- Effort: S
- Verify: a test that a second concurrent `GET /auth/me/export` for the same user gets 429; the loop-lag metric (REL-09) during a large export.

## Looked wrong, actually fine

- **WebSocket backpressure.** `safe_send_json` catches only `WebSocketDisconnect`/`RuntimeError` (`modules/chat/ws_limits.py:59-65`), but Starlette 1.3.1 turns any `OSError` on send into `WebSocketDisconnect`, and uvicorn 0.54's websockets-sansio protocol waits on `writable` before each send (flow control), raises `ClientDisconnected(OSError)` when the peer is gone, and pings every 20 s with a 20 s pong timeout (`.venv/.../uvicorn/protocols/websockets/websockets_sansio_impl.py:165-175, 347-371, 432-436`; `uvicorn/protocols/utils.py:10`). A stuck phone is dropped within ~40 s and the producer drains (`modules/chat/ws_turn.py:68-77`).
- **SSE queue is unbounded** (`modules/chat/stream_api.py:88`) — but one reply bounds it (8 192 output tokens), and the two `BaseHTTPMiddleware` layers pass the body through zero-buffer memory streams (`.venv/.../starlette/middleware/base.py:189-190`), so a slow client back-pressures the generator, not memory.
- **Hidden LLM retries.** OpenRouter calls go through LiteLLM's `base_llm_http_handler` (`.venv/.../litellm/main.py:3444-3512`), not the OpenAI SDK, so no SDK `max_retries`; every call site is inside `asyncio.timeout` (`gateways/litellm_gateway.py:82, 311`, `gateways/structured_completion.py:155`, `gateways/tool_completion.py:176`, `gateways/vision_completion.py:59`, `gateways/embedding_gateway.py:66`). No retry amplification found.
- **redis-py 8.1 default retries (10 with backoff)** apply only to a `Redis()` that builds its own pool; `redis.from_url` builds the pool first and each connection gets `Retry(NoBackoff(), 0)` (`.venv/.../redis/asyncio/client.py:206-209`, `connection.py:666-682`). "Fail fast" at the 5 s socket timeout holds.
- **DNS on the default executor.** uvicorn runs on uvloop (`uvloop` 0.22 installed by `uvicorn[standard]`, `--loop auto`), whose `getaddrinfo` uses libuv's own pool, so REL-03's starvation does not reach DNS for httpx, asyncpg or Redis.
- **Other `(x+)*`-shaped regexes.** `services/answer_check.py:106` (`_UNIT_TAIL`) is used with `.match` (no end anchor, greedy success, linear); `:157` needs `^digits` between repeats; `_SENTENCE_CLAIM` (`services/answer_fence.py:538`) measured linear (8 000 words, 1.8 ms). `modules/math/text_plot.py:23` (`_TABLE_RULE`) is quadratic in a row's leading whitespace (20 000 spaces → 2.8 s) but only runs on rows of a plain code block; covered by REL-01's class fix.
- **Physics symbolic parser** (`modules/physics/symbolic/parse.py`) bounds nodes, symbols and powers and is only used inside `run_sympy` (`modules/physics/prompt.py:89-97`), where a runaway is killed.
- **Chat-path embeddings** are bounded (`MEMORY_QUERY_EMBED_TIMEOUT_SECONDS=0.75` in `fly.toml`, RAG `_RAG_EMBED_TIMEOUT_SECONDS` in `modules/chat/history_rag.py:185-190`, `modules/attachments/rag.py:301-306`).
- **Per-token filters** (`modules/chat/stream_scaffold.py`, `gateways/think_stripper.py`, `modules/images/answer_photo.py:58-67`) trim their buffers or stop after `_WATCH_CHARS`; amortized linear.
- **Module-level state outside the SCALING tables** (full list in `scratch-rel/module_state.txt`): `background/periodic.py:31-35` (each worker's own scheduler tasks), `core/ids.py:16` (uuid7 monotonic lock; a turn's rows come from one machine), `gateways/mcp/registry.py:15` and `modules/chemistry/catalog.py:499` (filled at import/boot), `modules/attachments/thumbnails.py:35` (per-loop semaphore, documented as per process in `core/settings/attachments.py:36-37`), ContextVars (per task), `gateways/apple_auth.py:26-31` (JWKS cache with a single-flight lock). None needs cross-machine agreement.
- **Request body cap** is pure ASGI and innermost, so its 413 keeps CORS/request-id headers (`main.py:76-80`, `core/body_limit.py:39-92`).
- **Readiness** answers within Fly's 5 s check (`routers/health.py:15-48`).
