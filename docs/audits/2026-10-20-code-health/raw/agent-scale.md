### SCALE-01: Five unindexed foreign keys turn every message, chat and fact delete into full-table scans, so account and chat deletion fail at scale

- Severity: Critical (certain failure at scale: account deletion, which the stores and GDPR require, times out for active users)
- Confidence: High (mechanism). Size thresholds are estimates.
- Locations:
  - FK columns with no index whose leading column is the FK:
    - `apps/api/app/modules/memory/models.py:113-116` `source_message_id → messages.id ON DELETE SET NULL` (created `apps/api/alembic/versions/0087_memory_facts.py:127-134`, no index)
    - `apps/api/app/modules/memory/models.py:99-103` `superseded_by_id → memories.id ON DELETE SET NULL` (`0087_memory_facts.py:119-126`, no index)
    - `apps/api/app/modules/memory/models.py:110-112` `source_chat_id → chats.id ON DELETE SET NULL` (`0003_fk_cascades.py:30-38`, no index)
    - `apps/api/app/modules/todos/models.py:48-50` `chat_id → chats.id ON DELETE SET NULL` (`0008_create_todo_items.py:27-29`, no index)
    - `apps/api/app/models/orm/attachments.py:46-48` `message_chunks.chat_id → chats.id ON DELETE CASCADE`. Its only index is `(user_id, chat_id)` (`attachments.py:31`, `0064_message_chunks.py:48`), which cannot be searched by `chat_id` alone.
  - Deletes that fire those RI triggers once **per deleted row**:
    - Account delete: `apps/api/app/repositories/users.py:130-137` (`DELETE messages WHERE user_id`, then memories, todos, chats)
    - Delete all chats: `apps/api/app/modules/chat/service.py:139` → `apps/api/app/repositories/chats.py:256-270`
    - Delete one chat: `apps/api/app/modules/chat/service.py:161`
    - Regenerate (the finalize transaction): `apps/api/app/modules/chat/turn_settle.py:167`. Also `apps/api/app/modules/chat/turn_intercepts.py:57` and `apps/api/app/modules/attachments/workflow.py:177`
    - Fact deletes, including cap eviction on every extraction once a user is at 150 facts: `apps/api/app/modules/memory/writes_repository.py:173-174` → `apps/api/app/modules/memory/erase.py:53`. Also `apps/api/app/modules/memory/repository.py:59,142,160`
- Evidence: Postgres never indexes the referencing side. `ON DELETE SET NULL/CASCADE` runs `UPDATE ONLY memories SET source_message_id = NULL WHERE $1 = source_message_id` once for each deleted `messages` row, and the same for the other four constraints. Without an index each run is a sequential scan of the whole referencing table. The team fixed this exact class for the attachments module on 2026-10-19 (`f51358c9a`, #1909), in `0115_attachment_linked_at.py:13-15`: *"The indexes serve a message delete (FK SET NULL on `message_id`), a chat delete (FK CASCADE on `attachment_chunks.chat_id`)…"*. The memories, todos and message_chunks constraints were not covered. `delete_user` itself comments *"Deletes every user-owned row explicitly…"*, but deleting the user's messages first fires the memories trigger for every message:
  ```python
  await session.execute(delete(Message).where(Message.user_id == user_id))   # users.py:130: 1 memories seq scan per message
  await session.execute(delete(Memory).where(Memory.user_id == user_id))     # :131: 1 memories seq scan per fact (superseded_by_id)
  ...
  await session.execute(delete(Chat).where(Chat.user_id == user_id))          # :137: per chat: memories, todo_items and message_chunks scans
  ```
- Impact: a user with M messages, F facts and C chats costs (M + F + C) scans of `memories` plus C scans each of `todo_items` and `message_chunks`, inside one statement bounded by `DB_COMMAND_TIMEOUT_SECONDS` = 120 (`apps/api/app/core/settings/infrastructure.py:25`). PRODUCTION.md says that timeout is "generous because account delete is one cascading DELETE". At 300k registered users × ~50 facts, `memories` is ~15M rows (several GB of heap), so one scan takes seconds. An account with 2,000 messages, or a 300-message chat delete, cannot finish in 120 s: the statement is cancelled, the user gets 503 and the account stays. Even at 10k users (~0.5M facts, about 100 ms per scan), "delete all chats" or account delete for an active user is already at minutes. Every regenerate adds one `memories` scan to the finalize transaction, and the chat's next turn and its history reads wait on that finalize (`apps/api/app/modules/chat/finalize_registry.py:140-180`). Cap eviction adds 1–3 scans to every extraction job of a user at the 150-fact cap. Meanwhile the seq scans compete for Neon's small compute and cache.
- Fix: one expand migration, each index built `CREATE INDEX CONCURRENTLY` inside `autocommit_block` (the pattern of `0115`). Add `ix_memories_source_message (source_message_id) WHERE source_message_id IS NOT NULL`, `ix_memories_superseded_by (superseded_by_id) WHERE superseded_by_id IS NOT NULL`, `ix_memories_source_chat (source_chat_id) WHERE source_chat_id IS NOT NULL`, `ix_todo_chat (chat_id) WHERE chat_id IS NOT NULL` and `ix_message_chunks_chat (chat_id)`. Declare them in the ORM `__table_args__` so `alembic check` keeps passing. The partial predicates are implied by `col = $1` (a strict operator), so the RI query can use them. In the same pass, drop the now-redundant `ix_message_chunks_user` (see SCALE-14) to keep the index count flat on the largest table. Add an architecture test that fails when any ORM `ForeignKey` column has no index with that column leading, so this class cannot come back.
- Effort: S
- Verify: on a Neon branch seeded with 1M `memories` rows, run `EXPLAIN (ANALYZE, BUFFERS) DELETE FROM chats WHERE id = :chat_with_300_messages`. Before the fix, the plan shows `Trigger for constraint fk_memories_source_message_id: calls=300` with seconds of time. After it, milliseconds. Add the FK-index architecture test.

### SCALE-02: Fixed per-chat dedupe key plus the 24 h "done" marker: history compression runs at most once per chat per day, and the first run is a no-op

- Severity: High (the compaction the prompt design depends on effectively never runs. Long chats silently lose context after ~30 messages)
- Confidence: High
- Locations:
  - `apps/api/app/modules/chat/post_turn.py:178-194` (`f"compress:{ctx.chat_id}"`)
  - `apps/api/app/core/jobs/dedupe.py:20-27,89-100` (`_DEDUPE_DONE` for `_JOB_DONE_TTL_SECONDS = 86_400`)
  - `apps/api/app/core/jobs/worker.py:113-119,137-143` (any normal return → `_extend_dedupe`; a later entry with the same key → `"done"` → acked unrun)
  - Same class, smaller: `apps/api/app/background/handlers.py:217` (`memory_consolidate:{user_id}:lock{n}` is per user, so a second lock-busy consolidation within 24 h is acked as done and dropped). `apps/api/app/background/handlers.py:186-193` (the lesson_progress retry payload omits `assistant_message_id`, so retries 2+ fall back to the per-chat stem `lesson_progress:{chat_id}:lock{n}`). `apps/api/app/modules/attachments/jobs.py:21-23` (`attachment_index:{file}:{chat}`: a run skipped by `_unless_spend_capped`, `apps/api/app/background/handlers.py:110-123`, still returns normally, so the worker marks it done for 24 h even after the cap resets at 00:00 UTC). `apps/api/app/services/topic.py:61-74`: the handler deletes its own `jobdone:topic:` key "so a later retry can run", but the worker writes `done` right after the handler returns (`apps/api/app/core/jobs/worker.py:142`), so that release never takes effect.
- Evidence: the compress job is enqueued after every turn with a fixed key. The first one runs on turn 1, when `should_run_compression` finds nothing to fold and returns normally. The worker then stores `jobdone:compress:<chat>=done` for 24 h, and every later compress entry for that chat is acked as *"Skipping already-processed job"*:
  ```python
  # dedupe.py:89-98
  async def _extend_dedupe(redis, dedupe_key):
      await redis.set(job_done_key(dedupe_key), _DEDUPE_DONE, ex=_JOB_DONE_TTL_SECONDS)   # 86_400
  ```
  The compaction design needs a run whenever the gap reaches 3 messages: `apps/api/app/services/context_window.py:131-139`, *"Run compaction whenever that gap reaches `urgent_min_pending` … so the hole never grows past a few messages"*. The prompt includes at most 10 gap messages (`context_window.py:150-152`, `UNSUMMARIZED_GAP_MAX_MESSAGES = 10`). Intent check: the key came from `b0605b7ec` (2026-08-13, "perf(chat): dedupe compress job by chat") to *"coalesce rapid successive turns"*. The 24 h done marker already existed, so the key suppresses far more than in-flight duplicates. On 2026-10-19, `51f6dfd5b` introduced `unique_dedupe_key` precisely because *"A fixed key would have skipped those for 24h"*, but left `compress:` and the lock-retry stems fixed. `apps/api/app/tests/modules/chat/test_post_turn_jobs.py:75` pins the fixed key. No test covers "a second compress for the same chat runs".
- Impact: on any chat active within a day (nearly all of them), messages 21+ beyond the recent window and the 10-message gap are neither summarized nor sent. The model forgets mid-conversation context, which is the problem compression exists to solve, and nothing logs it. Fixing this exposes SCALE-03's compaction transaction (LLM call inside an open DB transaction), so fix both together.
- Fix: in `post_turn._compress_job`, use `jobs.unique_dedupe_key(f"compress:{chat_id}")`. The per-chat `chatcompress:` lock (`apps/api/app/modules/chat/compaction.py:32-35`) already serializes concurrent runs, and `should_run_compression` makes extra runs cheap. Make the lock-retry stems unique (`unique_dedupe_key(f"{stem}:lock{n}")`) and carry `assistant_message_id` in the lesson_progress retry payload. Give the worker a way for a handler to say "not done" (for example `raise JobSkipped` → release the key and ack), use it in `_unless_spend_capped`, and drop the topic handler's self-release. Add a test: two compress entries for one chat, the first a no-op, the second must run.
- Effort: S
- Verify: worker test with fakeredis: enqueue `compress` for chat X twice, the first run finding nothing to fold. Assert the second handler call happens. In production, the log count of `History compression` runs per chat per day exceeds 1 on long chats.

### SCALE-03: Pooled DB connections held idle-in-transaction across R2 I/O, waits and an LLM call, so one gallery open or an R2 slowdown can drain a machine's 30-connection pool

- Severity: High (a user action or a dependency slowdown takes the chat path down on that machine)
- Confidence: High that the connection is held (SQLAlchemy autobegin). Medium on how often the pool is exhausted (depends on R2 latency and concurrency).
- Locations:
  - Thumbnails: `apps/api/app/modules/attachments/api.py:176-187` (`session = Depends(get_db)`) → `apps/api/app/modules/attachments/workflow.py:295` (`_verified_row` SELECT, `:68`) → `:299` `thumbnail_bytes`, which does R2 GET, waits on a **2-slot** limiter, does a full-image GET, resizes and PUTs (`apps/api/app/modules/attachments/thumbnails.py:102-122`; limiter `apps/api/app/core/settings/attachments.py:37` `attachment_thumbnail_concurrency: int = 2`)
  - Upload confirm: `apps/api/app/modules/attachments/workflow.py:257` (SELECT) → `:265` `ensure_verified_or_purge` → `apps/api/app/modules/attachments/content.py:267` (full-object R2 download, up to 12 MiB) → `content.py:335` (`mark_verified`)
  - Unverified file read: `apps/api/app/modules/attachments/workflow.py:68-82`
  - Message history: `apps/api/app/modules/chat/service.py:216-219`. `get_chat` (SELECT) is followed by `wait_for_inflight_stream` (≤10 s) and `wait_for_pending_finalize` (≤10 s polling, `apps/api/app/modules/chat/finalize_registry.py:40,129-178`) before the page query. Phones reload the chat after every deploy reconnect. Same order in feedback: `service.py:282-284` (`get_chat` then a finalize wait).
  - Account delete: `apps/api/app/modules/attachments/lifecycle.py:118-144` (`list_for_user` SELECT, then one R2 delete plus one prefix list/delete **per file**, fanned out unbounded with `asyncio.gather` at `:55-60`, all while the request transaction is open), followed by SCALE-01's cascade
  - Job: `apps/api/app/modules/chat/compaction.py:37-89`. The session reads chat, count, window and range, then `summarize_conversation` (LLM: up to `background_llm_timeout_seconds` 60 s primary + 60 s fallback, `apps/api/app/gateways/litellm_gateway.py:71-106`), then commits. The `chatcompress:` lock TTL is 120 s (`compaction.py:22`), equal to the worst-case call, and is not refreshed.
- Evidence: CLAUDE.md, *"Slow provider calls should run outside an open DB transaction"*. `get_by_id` executes on the request session and never commits, so the connection stays checked out until `get_db` closes it after the handler (`apps/api/app/core/db.py:46-48`). Pool: `db_pool_size` 20 + `db_max_overflow` 10, `pool_timeout` 5 s (`apps/api/app/core/settings/infrastructure.py:17-19`). The rest of the codebase follows the rule deliberately (`apps/api/app/background/push_scheduler.py:28-30`, `apps/api/app/modules/memory/apply.py:1`, `apps/api/app/modules/chat/history_rag.py:44`, `apps/api/app/modules/notifications/reminder_email.py:88-90`). These paths are the exceptions.
- Impact: the Library grid requests one `?w=` thumbnail per tile. On first view of N new photos, N requests each hold a pooled connection while queuing two at a time for R2 download + resize + upload (~0.5–1 s each), so 25 tiles hold most of a machine's 30 connections for ~10 s. Chat turns on that machine then fail `pool_timeout` after 5 s and answer 503. When R2 is slow (botocore up to 5 s connect + 20 s read × 3 attempts, PRODUCTION.md), every confirm/thumbnail holds a connection for up to a minute, so an R2 slowdown becomes an API outage. Through Neon's transaction-mode pooler, an open transaction also pins a *server* connection. A deploy (all phones reload chats at once) parks history reads on connections for up to 10 s each. Compaction holds a worker connection idle-in-transaction for up to 120 s per job (masked today by SCALE-02).
- Fix: read the row, then `await session.commit()` (or use a short `async with SessionLocal()` block and `expire_on_commit=False`, already set) **before** any R2 call or wait. Re-open a session only for the follow-up write (`mark_verified`, `_drop_row_for_missing_file`). In `list_messages_page` and `set_message_feedback`, wait for the stream/finalize *before* the first query. In compaction, read in one short session, summarize with no session, then write `summary`/`summary_message_count` with a compare-and-set (`WHERE summary_message_count = :already`) in a second session, so a concurrent run cannot clobber it. Account delete: move per-file R2 deletes to the `storage_sweep` job (it already deletes the `{user_id}/` prefix) or bound the fan-out with a semaphore and commit before it. Seam: the attachment workflow and `modules/chat/compaction.py`. A test that asserts "no checked-out connection during gateway calls" (fake gateway that inspects `engine.pool.checkedout()`) keeps it fixed.
- Effort: M
- Verify: a load test with a fake slow storage gateway (2 s per read) and 30 concurrent `/attachments/{id}/file?w=256`. Before: `engine.pool.checkedout()` reaches 30 and a concurrent `/chats` request gets 503. After: checked-out stays near 0. In production, `pg_stat_activity` rows in `idle in transaction` from the API role.

### SCALE-04: Every minute, the reminder schedulers scan every open dated to-do of every user with no usable index, and the token lookup hits a hard parameter cliff

- Severity: High (load that grows with all-time to-do volume, paid every minute, plus a cliff that stops reminder delivery for everyone)
- Confidence: High (missing index, unbounded scan). Medium (the exact user count where the cliff hits).
- Locations:
  - `apps/api/app/modules/notifications/push.py:246-261`, push candidates (no `user_id` predicate, no LIMIT)
  - `apps/api/app/modules/notifications/push.py:211-224`, `log_aged_unsent_reminders`, a second cross-user count every cycle
  - `apps/api/app/modules/notifications/reminder_email.py:52-65`, the email scheduler's copy of the scan, also every minute (`apps/api/app/core/settings/notifications.py:14,16`: on by default)
  - Only candidate index: `apps/api/alembic/versions/0021_perf_indexes.py:21-23` `ix_todo_user_open_due ON todo_items (user_id, due_at) WHERE checked = false AND due_at IS NOT NULL` (ORM `apps/api/app/modules/todos/models.py:31-36`)
  - `apps/api/app/modules/notifications/push.py:265` → `apps/api/app/repositories/push_tokens.py:151-156`: `PushToken.user_id.in_(user_ids)` with one bound parameter per distinct user
  - Cadence: `apps/api/app/background/push_scheduler.py:24`, `apps/api/app/background/email_reminder_scheduler.py:23` (60 s)
- Evidence:
  ```python
  # push.py:246-259: no user_id, so the (user_id, due_at) partial index cannot seek
  select(TodoItem, User).join(User, User.id == TodoItem.user_id).where(
      TodoItem.checked.is_(False), TodoItem.due_at.isnot(None),
      TodoItem.notification_sent_at.is_(None),
      User.push_notifications_enabled.is_(True), User.push_reminders_enabled.is_(True),
      TodoItem.due_at >= overdue_cutoff, TodoItem.due_at <= window_end)   # [now-48h, now+60m]
  ```
  The only index on `due_at` leads with `user_id`, so the planner can only seq-scan `todo_items` (all-time rows, checked ones included: nothing ever purges them) or full-scan the partial index. Secondary: SQLAlchemy renders `.is_(False)` as `checked IS false`, while the partial predicate is `checked = false`. On PG 16 (CI image `pgvector/pgvector:pg16`, `.github/workflows/api-ci.yml:48`) the prover may not treat these as equivalent, which would also keep per-user queries such as `apps/api/app/modules/todos/repository.py:37` off this index (confirm with EXPLAIN). The candidate set never shrinks for most users: push is on by default (`apps/api/app/models/orm/user.py:79-85`, `push_notifications_enabled`/`push_reminders_enabled` default true), and a user without a device token is skipped without being marked (`push.py:283-292`, *"everyone who denied the OS permission lands here every minute for 48h"*). The same applies to rows in quiet hours or before their lead time.
- Impact: three cross-user scans a minute (two push, one email) whose cost grows with all-time to-do volume, not with due reminders. At 100k DAU, with tens of millions of to-do rows after a year, that is GBs of reads a minute on Neon's small compute and a compute that never scales to zero. The cliff: asyncpg refuses more than 32,767 bind parameters. Once more than ~32k distinct users have an unsent reminder in the 49-hour window (tokenless users count, and they linger 48 h), `list_for_users` raises. `run_locked_cycle` logs "push cycle failed" (`apps/api/app/background/periodic.py:97-98`) and **no one** gets a reminder until the window drains.
- Fix: expand migration (CONCURRENTLY): `CREATE INDEX ix_todo_push_due ON todo_items (due_at) WHERE checked = false AND notification_sent_at IS NULL AND due_at IS NOT NULL`, and the email twin on `email_sent_at IS NULL AND recurrence_rule IS NULL`. Write `checked = false` (`TodoItem.checked == False`, `# noqa: E712`) so the partial predicate matches. Keyset-page the candidates (`ORDER BY due_at, id LIMIT 500`), and chunk the token lookup (or `= ANY(:ids)` with one array parameter). ### SCALE-08: The job backlog is never measured, and the stream trims can silently drop jobs that were never delivered. The DLQ alert is level-based on a stream that never drains

- Severity: Medium (silent loss of titles, memory, indexing and emails during a worker outage or a sustained backlog, plus alert fatigue that hides real incidents)
- Confidence: High
- Locations:
  - `apps/api/app/core/jobs/queue.py:18-19,107-128`: soft trim on every enqueue. With **no pending entries** it runs `XTRIM MAXLEN ~ 10_000`.
  - `apps/api/app/core/jobs/queue.py:79-104`: hard cap `JOBS_STREAM_MAX_LEN` 50,000 on every XADD (`apps/api/app/core/settings/worker.py:15`)

  ```python
  # queue.py:123-126
  if min_id:
      await redis.xtrim(JOBS_STREAM, minid=min_id, approximate=True)
  else:
      await redis.xtrim(JOBS_STREAM, maxlen=_MAXLEN, approximate=True)   # drops undelivered jobs too
  ```
  "Nothing pending" is exactly the state when no consumer is reading: the worker group is scaled to 0, failed to start (a bad release crash-looping before its first read), stopped while idle, or wedged in `_wait_for_group`. During that state every API enqueue cuts the backlog back to ~10k, oldest first, with no log (the trimmed ids were never delivered, so `_ack_trimmed_entries` never sees them). With consumers up, a backlog beyond 50k is cut the same way by the hard cap. The PEL alert (≥ 50) cannot see a backlog: a worker's PEL is at most its 8 running + 200 waiting entries, however long the queue is.

That is the alert most likely to be muted, and with it the signal for a real DLQ surge.
- Fix: never trim below the undelivered tail. Read the group's `last-delivered-id` (`XINFO GROUPS`) and trim `MINID` at min(oldest pending, last-delivered + 1), dropping the `MAXLEN 10_000` fallback. Keep the hard cap only as a memory guard and count what it drops (compare `XLEN` before/after, or `XINFO STREAM` `first-entry` vs last-delivered). Report backlog = `lag` from `XINFO GROUPS` (Redis ≥ 7) or `XLEN` minus acked history, plus the age of the oldest undelivered entry. Emit that from the **API** process too (any machine, under a short Redis lock) so a dead worker group is visible. Make the DLQ alert rate-based (new DLQ entries per interval, from the `failed_at` field or a counter) and give DLQ entries an age-based trim (for example 7 days) via `XTRIM MINID`. Seam: `core/jobs/queue.py`, `core/jobs/admin.py`. SCALING.md item 2 plans to move this trim onto a timer. Moving it unchanged would keep the unsafe fallback, so fix the trim first. Update PRODUCTION.md/SCALING.md wording.

Only `welcome:` / `receipt:` (`apps/api/app/modules/notifications/jobs.py:15,40`) and the once-per-chat `topic:` need a long window.
- Impact: ~1–2 keyed jobs per turn × 24 h of turns is a few million live keys at 100k DAU (~150 B each with TTL), hundreds of MB of Upstash memory, billed and shared with rate limits, quotas and auth revocation. SCALING.md item 6 ("make the account-delete sweep independent of total size") understates its own problem: the keyspace that `SCAN MATCH *<uuid>*` walks on every delete is dominated by these markers.
- Fix: a per-job done TTL. `register(job_type, handler, done_ttl=…)` with a default of 1 h (or 15 min). Keep 24 h for `transactional_email` and `storage_sweep`. Seam: `core/jobs/queue.register` + `dedupe._extend_dedupe`.
- Effort: S
- Verify: Upstash key count / `INFO keyspace` before and after. Unit test: a `message_index` success sets a TTL ≤ 3600.

### SCALE-13: Redis key hygiene: six INCR-then-EXPIRE pairs are not atomic, and two Redis sets have no TTL and no size bound

- Severity: Low
- Confidence: High
- Locations:
  - Non-atomic INCRBY/HINCRBY/SADD then EXPIRE, where a crash or task cancellation between the two leaves a key with no TTL: `apps/api/app/services/quota/tokens.py:149-151` and `:199-201` (daily usage; the TTL is only set when `new_total == requested`, so a racing first writer that dies leaves the day's key immortal), `apps/api/app/services/quota/live_talk.py:106-108`, `apps/api/app/core/spend_counter.py:57-59`, `apps/api/app/gateways/structured_completion.py:105-106`, `apps/api/app/modules/memory/extract_backlog.py:146-147`, `apps/api/app/modules/memory/history_scan.py:121-122,131-132`. The team already fixed this class in `apps/api/app/services/quota/counters.py:81-107` (*"INCRBY and `EXPIRE … NX` run in one transaction, so no charge is left without a TTL"*) and `apps/api/app/core/rate_limit.py:19-20`.
  - No TTL, unbounded: `apps/api/app/modules/attachments/lifecycle.py:23,69-76` (`recall:storage:pending_delete` SADD). It is read whole with `SMEMBERS` and retried every reaper cycle (`:80-103`), so a key that fails permanently stays forever, and an R2 outage during peak deletes grows it without limit. Also `apps/api/app/modules/notifications/push.py:50,75-84` (`recall:push:receipts:pending` ZSET), bounded only while the push cycle runs, and read with an unbounded `ZRANGEBYSCORE` (SCALE-05).
- Impact: small per key, but immortal dated keys accumulate with every crash or cancel during a reservation (for example a client disconnect cancelling the turn task between INCRBY and EXPIRE), and the pending-delete set can grow until one reaper cycle cannot finish its SMEMBERS-and-retry pass.
- Fix: route all of them through the existing transactional pattern (`pipeline(transaction=True)` with `INCRBY` + `EXPIRE … NX`, as in `counters._reserve_daily_slot`). Give the pending-delete set a sorted-set form with attempt counts and a cap (move to a dead set after N failures) and read it with `SSCAN`/`ZRANGE … LIMIT`.
- Effort: S
- Verify: a unit test per site that cancels between the two commands (fakeredis + a patched expire raising `CancelledError`) and asserts `TTL >= 0`.

### SCALE-14: Redundant indexes on the hottest insert tables

- Severity: Low
- Confidence: High
- Locations: `ix_messages_chat_created (chat_id, created_at)` (`apps/api/app/models/orm/chat.py:67`, `alembic/versions/0002_indexes_and_constraints.py:22`) is a prefix of `ix_messages_chat_created_id (chat_id, created_at, id)` (`chat.py:73`, `0063_msg_chat_created_id_idx.py:33`). `ix_message_chunks_user (user_id)` (`apps/api/app/models/orm/attachments.py:30`, `0064_message_chunks.py:47`) is a prefix of `ix_message_chunks_user_chat` (`:31`, `0064:48`). `ix_message_chunks_message (message_id)` (`:32`, `0064:49`) is a prefix of the unique `uq_message_chunks_message_index (message_id, chunk_index)` (`:29`, `0064:42`). `ix_todo_user_topic (user_id, topic)` (`apps/api/app/modules/todos/models.py:26`, `0012_add_todo_topic.py:26`) is a prefix of `ix_todo_user_topic_sort` (`:27`, `0018_add_todo_sort_order.py:22-26`).
- Evidence: a btree whose columns are a leading prefix of another btree on the same table serves no query the longer one cannot. `messages` takes 2 inserts per turn into 6 indexes (one of them the trigram GIN, SCALE-11). `message_chunks` takes 3–12 inserts per turn into 5 indexes (one of them HNSW).
- Impact: extra WAL, write I/O and storage on every turn with no read benefit. Small per row, large at volume.
- Fix: drop the four (contract migration, `DROP INDEX CONCURRENTLY`, with an `# expand-contract:` note per `docs/ROLLBACK.md`) and remove them from the ORM `__table_args__`. Pair with SCALE-01 so `message_chunks` swaps `(user_id)` for the needed `(chat_id)`.
- Effort: S
- Verify: `pg_stat_user_indexes.idx_scan` stays ~0 for the four over a week before dropping. After the drop, `EXPLAIN` of the chat window and chunk queries still uses the longer indexes.

### SCALE-15: Job types and payloads have no expand/contract rule: a worker that does not know a type dead-letters it, which happens during every blue-green overlap and after any rollback

- Severity: Low
- Confidence: Medium (the window is short. A rollback makes it certain for the jobs queued under the newer release.)
- Locations: `apps/api/app/core/jobs/queue.py:131-140` (unknown type or bad JSON → `JobDiscardError` → DLQ, no retry, `apps/api/app/core/jobs/worker.py:144-147`). Handlers read required fields with `payload["…"]` (for example `apps/api/app/background/handlers.py:141-146,170`), so a payload shape the running worker does not expect fails three times and is dead-lettered. `docs/ROLLBACK.md` "Schema changes: expand, then contract" covers tables only. `docs/SCALING.md:33` says *"Two workers overlap for a moment; leases, dedupe and scheduler locks cover it"*.
- Evidence and impact: in a blue-green deploy the new API machines enqueue while the old worker still consumes. A job type added in the release (or a renamed or required payload field) is dead-lettered by the old worker. After a rollback, every such job already in the stream is dead-lettered by the restored worker. Because replay is manual (SCALE-09), that work is lost unless someone notices.
- Fix: on an unknown type, do not dead-letter. Leave the entry pending (no ack) so a worker that knows the type reclaims it, or re-enqueue with a delay, with a bound such as 24 h before the DLQ. Write handlers to accept the previous payload shape for one release (`payload.get` with defaults), and add a line to `docs/ROLLBACK.md`: new job types and payload fields follow expand/contract.
- Effort: S
- Verify: a worker test with an entry of an unregistered type: it stays deliverable (not in the DLQ), and once the handler is registered it runs.

## Looked wrong, actually fine

- **A 900 s job against a 60 s reclaim.** Peers cannot double-run it. Every held entry's idle time is reset every 20 s by one `XCLAIM … JUSTID` (`apps/api/app/core/jobs/inflight.py:33,102-112`). The `jobdone:` running claim (300 s) is refreshed every 150 s while the handler runs (`apps/api/app/core/jobs/dedupe.py:103-120`). A peer that still reclaims (event loop blocked > 60 s) sees "in_flight" and gives the delivery back without counting it (`dedupe.py:132-159`). Every enqueue site now passes a dedupe key (`51f6dfd5b` added the last three).
- **Crash or deploy mid-job.** A `CancelledError` leaves the entry pending and releases only a claim this run owns (`apps/api/app/core/jobs/worker.py:85-94`). Entries delivered more than 5 times go to the DLQ on reclaim (`apps/api/app/core/jobs/pending.py:59-92`). Trimmed-but-pending ids are acked (`pending.py:20-40`). A consumer is removed only when it owns nothing (`pending.py:95-110`).
- **The `MINID` trim path** (`apps/api/app/core/jobs/queue.py:123-124`) only removes entries older than the oldest pending one, which are acked. Only the `MAXLEN` fallback and the hard cap are unsafe (SCALE-08).
- **Billing reconcile overrunning its lock.** It refreshes the lock after every user and stops if the lock is lost (`apps/api/app/background/billing_reconcile_scheduler.py:66-68`). Its `plan = :p` keyset page has no `plan` index, so each hourly cycle walks the users PK once per paid plan. That is acceptable at hourly cadence (and SCALING.md item 7 covers the RevenueCat side).
- **The chat-turn DB path** uses short per-step sessions (`apps/api/app/modules/chat/turn_load.py:79-200`), overlaps independent reads, and caps one turn's concurrent checkouts with `context_db_concurrency` = 3 (`apps/api/app/modules/chat/prompt_context.py:110-112`, `apps/api/app/core/settings/infrastructure.py:32`). The attachment-RAG lane holds no pool slot during its embed (`prompt_context.py:164-165`).
- **Most jobs keep provider calls outside transactions.** Memory apply writes text, releases the session, embeds, then writes vectors (`apps/api/app/modules/memory/apply.py:43-117`). The title job opens its session only after the LLM call (`apps/api/app/services/topic.py:33-48`). The to-do sync closes its session before extraction (`apps/api/app/modules/todos/sync.py:151-179`). History-RAG indexing never holds a session during the embed (`apps/api/app/modules/chat/history_rag.py:44-70`). The attachment index works in phases (`apps/api/app/modules/attachments/rag.py:205-263`). The email cycle rolls back before sending (`apps/api/app/modules/notifications/reminder_email.py:88-90`), and the push cycle releases its session before Expo (`apps/api/app/background/push_scheduler.py:30-41`). Only compaction breaks the rule (SCALE-03).
- **Row-lock ordering.** Memory writers and account delete both lock `users` first (`apps/api/app/modules/memory/writes_repository.py:51-55`, `apps/api/app/repositories/users.py:128-129`). The attachment indexer locks chat (`FOR KEY SHARE`) before attachment (`FOR UPDATE`), matching the chat-delete cascade (`apps/api/app/modules/attachments/chunks_repository.py:60-76`). No inverted pair was found.
- **Redis SET without TTL.** An `ast` scan of every `.set(key, value, …)` in `apps/api/app` found 58 calls, all carrying `ex=` or `keepttl=` (`tmp/code-audit/raw/scratch-scale/redis_set_ttl.py`). The counter refund Lua never creates a key (`apps/api/app/services/quota/counters.py:63-71`). Remaining gaps are only the INCR/SADD pairs in SCALE-13.
- **Account export** is streamed and every section is capped (`apps/api/app/modules/account/export.py:45-58`).
- **The orphan reaper** uses its partial index (`ix_attachments_unlinked_created`, `0115_attachment_linked_at.py:46-52`) and deletes DB-first, then storage.
- **Superseded memories do not pile up.** Cap eviction *deletes* rows with their history (`apps/api/app/modules/memory/writes_repository.py:172-174`). Superseded chains only come from explicit corrections.
- **Duplicate history-scan jobs** (the 30 min queued marker can lapse before a backlogged scan runs) are cheap: the scan returns at once when `memory_history_scanned_at` is set (`apps/api/app/modules/memory/history_scan.py:152-156`).
- **History and list endpoints** are bounded: chat list cap 200 (`apps/api/app/repositories/chats.py:76-95`), message pages use the `(chat_id, created_at, id)` cursor, to-dos cap at 1000 (`apps/api/app/modules/todos/repository.py:47-69`), and the gallery is limit/offset.

## Open questions for the team

1. Which pgvector version runs on the production Neon project? With 0.8+ the planner costs HNSW+filter differently and `hnsw.iterative_scan` exists, which decides which way SCALE-06 fails.
2. Which Postgres major version runs in production (CI uses `pg16`)? It decides whether `checked IS false` can use the `checked = false` partial index (SCALE-04).
3. Throughput plan for workers: with `JOBS_WORKER_CONCURRENCY` 8 and LLM-bound jobs of a few seconds, one worker clears roughly 100 jobs a minute. Peak post-turn volume at 100k DAU is thousands a minute. Is the plan dozens of workers, or a higher per-worker concurrency for I/O-bound jobs (memory budget permitting)? SCALE-08's backlog metric is needed to tell.
4. Is chat-history RAG meant to search a user's entire history forever? That is the product decision behind SCALE-10's retention window.
5. Was the 24 h suppression of `compress:{chat_id}` ever intended as cost control (SCALE-02)? The compaction docstring and `should_run_compression` say the opposite.
6. Do production indexes exist that are not in migrations (added by hand during an incident)? `alembic check` only compares the ORM with the migrated CI database, so a manual `memories.source_message_id` index would change SCALE-01's urgency (not its fix).
7. What is the Upstash plan's data-size and connection limit? It sizes SCALE-12 and SCALING.md item 2.
8. Does Fly's blue-green on the `worker` process group overlap old and new workers, and for how long? That is the SCALE-15 window.
