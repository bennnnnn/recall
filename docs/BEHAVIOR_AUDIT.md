# Recall behavior audit

Where Recall stands against the target behavior spec: how a finished Recall should behave in
conversation, memory, model routing, tools and search, the chat interface, features, safety and
engineering reliability. Each requirement has a status, file:line evidence, one concrete test case
and where that test belongs, and a fix sketch for anything short of a pass.

Audited on `main` at `3db7f6d` (19 Oct 2026), read-only, from code and the offline suites. No
model provider was called, so answer quality itself (tone, structure, whether a reply follows its
prompt) is marked **LIVE-EVAL**: the code can only set it up, and the table says how well it does.
Security, billing, deploy/ops, the server chat path and store compliance were reviewed separately
before launch; their fixes are on the `claude/*` branches named in the tables (**REVIEWED**).

## Statuses

| Status | Meaning |

## Biggest gaps, in priority order

1. **Multi-intent requests.** Nothing splits a message into tasks, so "a laptop and remote jobs"
   gets one unsectioned answer with no search, and deterministic paths swallow the second request:
   a reminder replaces the answer to a question, two reminders merge into one with the wrong time,
   and "switch to dark mode and tell me a joke" drops the switch (I1, I2, I4, I6, D1).
2. **Honesty of claims.** A reminder is claimed as set before the tap (T5.5, F8.5); "where do I
   live?" denies a saved fact (M15); a memory failure looks like "nothing saved" (M17); a failed
   search looks like an empty one (D11.6); off-topic search results are forced into an answer (D11.2).
3. **Memory relevance and control.** Memory is off on most technical turns (M2), floods the prompt
   on an embed timeout (M6), can't be muted (M11), and leaks back through past-chat recall after the
   switch is off or a fact is deleted (M13, M14). "Forget" deletes broader facts than asked (M10).
4. **Streaming shows intermediate content.** Lesson cards stream as raw JSON, half tables as pipes,
   and verified-math markers and function-call blobs stay visible until `done` (S7.4-S7.6); a photo
   lookup shows the image-generation card (S7.9); the web slice shows cards as raw JSON (O10.2).
5. **Routing blind spots.** Job openings and prices hinge on one 4-second classifier call (T5.2,
   T5.8); one image pins later turns to the fast photo model (R4.4); models carry no capability
   flags, so photo-turn fallbacks can't read images (R4.13); hard reasoning and code review stay on
   the fast model (R4.3, R4.6).
6. **The tests can't see most of this.** Battery and sweep record one outcome per turn, the battery
   harness turns memory off and hard-codes the model, and there is no E2E or web test in CI. Adding
   the test cases below as `gap` entries first makes each fix flip one strict expected failure
   (`apps/api/app/tests/behavior/cases.py`, `sweep_corpus/*.json`).

## How to use this file

- A FAIL or PARTIAL row is done when its test case exists in the named place and passes. Where a
  test case says battery or sweep, add it with a `gap` line first, so CI holds it as an expected
  failure until the fix lands (CLAUDE.md, "Behavior battery").
- LIVE-EVAL rows need `./scripts/dev.sh battery` against a real model (see `scripts/battery.py`);
  the battery report is where a reviewer judges them.
- Update a row's status in the same pull request that changes it.

4. **Routing knows little about models or tasks (R4.3, R4.6, R4.9, R4.13-R4.15):** no image, tool, JSON or context-size flags; hard reasoning and unfenced code review stay on the fast model; requested JSON is never checked; rules live only in code; the battery and sweep never check the chosen model.
5. **Search quality and honesty (T5.9, T5.11, D11.2, D11.6):** no preference for trustworthy sources; off-topic results forced into an answer; reply links never checked against what was found; a failed search reported like an empty one.
